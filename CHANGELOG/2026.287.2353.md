## Summary

**Leg 5 of `opencharly/opencharly#481` (`plugin-settings`) — the lane whose job was a DECISION, not a rename, and the decision is: `engine.build` retires to NOTHING.**

The operator's scope for #481 is **the image BUILDER only**, and `engine.build` **is** the builder selector: the contract deleted the field (spec leg 1, `EngineConfig` has no `Build`), so the setting can no longer be read, written or resolved. `engine.run` — which engine **runs** containers — is a different concept and is untouched, exactly as the scope ruled.

**What the retirement owes, and it is not just a deletion:** a user who once set `engine.build` will reach for it again. `charly settings get|set|reset engine.build` therefore answers as a **RETIREMENT, by name** — what removed it (the image builder is BuildKit, which is not a container engine and cannot be selected like one) and what did **not** change (`engine.run` is unaffected) — instead of a bare `unknown config key`, which reads as a typo and sends the user hunting for a setting that is deliberately gone. The answer lives in **ONE record** (`retiredSettings()`), consulted by all four entry points.

The first version of this change put the retirement check in `GetConfigValue`, and **every unit arm passed while the live command still said `unknown config key "engine.build"`**. `charly settings get` does not call `GetConfigValue`; it calls `resolveSettingsGet`, which dispatches the grammar, looks the key up in the listing and reaches **its own** generic unknown-key error **without ever delegating**. Fixed at that entry point, and the test table now drives **both** paths — `get (function)` and `get (CLI entry point)`. That is the difference between testing the **function** and testing the **SURFACE**.
